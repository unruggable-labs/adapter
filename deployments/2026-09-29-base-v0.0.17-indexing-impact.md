# Adapter v0.0.17 — Base indexing impact of the upgrade (2026-09-29)

**Chain:** Base mainnet (8453)
**Proxy:** `0x270d25D2c59A8bcA1B0f40ad95fF7806c0025c27` (live implementation `0x0f81bd4EDD4879734361A1A44460264CBf6F94c9`, source baseline `a20035c`)
**Question (Prem):** does upgrading to v0.0.17 affect indexing of the existing contract, or does it only add things?

## Conclusion

- **History is unaffected.** Logs already emitted are immutable and keep decoding with the `a20035c` ABI.
  The upgrade only changes what the proxy emits from the upgrade transaction onward.
- **The upgrade is not purely additive.** Five counterfactual setter events change signature, three events
  are no longer emitted, one event keeps its topic but changes the meaning of its indexed key, and four
  functions are removed.
- **In practice nothing that has been used on Base changes.** Every event emitted since deployment either
  keeps its exact signature and meaning, or (in one case) is a single record. None of the changed or
  removed events has ever been emitted on Base.
- **Indexer cutover is not a blocker for the Base upgrade.** An indexer that handles `AgentBound`,
  `AgentURISet`, `AgentWalletSet`, `AgentWalletUnset` and `MetadataSet` keeps working unchanged. To see
  the new behaviour it should add the new events below and accept `AgentBound` standards 3–7.

## Event-by-event comparison

Signatures and topics come from compiling `a20035c` (`src/Adapter8004.sol`) and v0.0.17
(`src/AdapterImplementation.sol`) with `forge inspect … events`.

### Unchanged (same topic, same meaning)

| Event | Topic |
|---|---|
| `AgentBound(uint256,uint8,address,uint256,address)` | `0x1cb39fc1…664c` |
| `AgentURISet(uint256,string,address)` | `0x6d0c5531…890f` |
| `AgentWalletSet(uint256,address,address)` | `0xc8982c1a…933b` |
| `AgentWalletUnset(uint256,address)` | `0x91aee750…b8eb` |
| `MetadataSet(uint256,string,bytes,address)` | `0x7014861b…18b6` |
| `Initialized(uint64)`, `OwnershipTransferred(address,address)`, `Upgraded(address)` | standard OZ |

`AgentBound`: same topic and indexed fields. The third field is renamed `tokenContract` → `boundAddress`
(names are not part of the topic). The `standard` enum gains values 3–7; 0–2 keep their meaning, and
address-type standards 5–7 use token ID 0. An indexer that rejects values above 2 must be widened.

### Same topic, changed meaning

| Event | Topic | Change |
|---|---|---|
| `CounterfactualAgentRegistered(bytes32,address,uint256,uint8,string,(string,bytes)[],address)` | `0x97d00c85…d2de` | The indexed `bytes32` key changes formula: old `keccak256(abi.encode(chainId, proxy, tokenContract, tokenId))`; new `keccak256(abi.encode(interoperableAddress(proxy), standard, boundAddress, tokenId))`. Decodes cleanly either way, so an indexer that is not cut over would silently file new records under a key that old records never used. |

### Changed signature (old topic stops, new topic starts)

v0.0.17 inserts `uint8 standard` after `tokenId`, and the setters now return the key.

| Event | Old topic (`a20035c`) | New topic (v0.0.17) |
|---|---|---|
| `CounterfactualAgentURISet` | `0xad589c9a…876b` | `0x208006a8…3032` |
| `CounterfactualAgentWalletSet` | `0x6301bb32…c401` | `0xe8fa7383…b7e8` |
| `CounterfactualAgentWalletUnset` | `0xe9f90502…651f` | `0x531cc4f9…03d8` |
| `CounterfactualMetadataSet` | `0xbb851dfc…3e21` | `0xe180e66f…b745` |
| `CounterfactualMetadataBatchSet` | `0x06c5400e…d745` | `0xeae9f308…715a` |

### No longer emitted

| Event | Topic | Why |
|---|---|---|
| `MetadataBatchSet(uint256,uint256,address)` | `0xfde0abed…35ed` | `setMetadataBatch` keeps its selector but now emits one `MetadataSet` per entry (already understood by existing indexers). |
| `BindingMetadataRewritten(uint256,address)` | `0xd8258bc5…c638` | `rewriteBindingMetadata` removed. |
| `IdentityRegistryUpdated(address,address,address)` | `0x196c4169…b8d9` | `setIdentityRegistry` removed; the registry is an implementation immutable. |

### New (additive)

| Event | Topic |
|---|---|
| `WalletUBIDSet(address,bytes32,address,uint256,uint8,address)` | `0x5b2d8053…54d8` |
| `WalletUBIDCleared(address,address)` | `0x603a2968…6506` |
| `Attested(address,uint8,bytes32,bytes32,bytes32,bytes)` | `0x04eac862…5220` |
| `AttestationRevoked(bytes32,address)` | `0x59d1b98a…c8b0` |

Wallet UBID claims are event-only: the latest `WalletUBIDSet` per account wins, and
`WalletUBIDCleared` unsets it.

### Removed functions (callers, not indexers)

`registrationHash(address,uint256)` (replaced by `hashBinding` / `bindingHashOf` with the new formula),
`setIdentityRegistry(address)`, `rewriteBindingMetadata(uint256)`, and the two-argument
`initialize(address,address)`. Anything that calls these on the proxy will revert after the upgrade.

history; a post-upgrade lookup for the same token computes a different key, so it will not match.

## Known consumers checked

A search of the local projects found no indexer or on-chain reader of the adapter's events or
`registrationHash`. Documentation to update after the upgrade:
- `adapter-app/src/app/page.tsx` describes `setIdentityRegistry`, which v0.0.17 removes.
- `id2/id-app/content/docs/user/contracts.mdx` lists implementation addresses `0x445229fa…9213`
  (Ethereum) and `0x7Cdba6F5…8cf2` (Base), which are already stale; the live ones are `0xa6D23f27…135f`
  and `0x0f81bd4E…94c9`, and they change again with this upgrade.

External indexers cannot be enumerated from here; they are affected only if they decode the
counterfactual events or call `registrationHash`.

## Cutover guidance

1. Record the upgrade boundary at the proxy's `Upgraded(newImpl)` log: block, block hash, tx index,
   log index. Decode with the `a20035c` ABI before it and the v0.0.17 ABI after it, including within
   the same block.
2. Keep old counterfactual keys as historical keys; do not recompute them with the new helper.
3. Add the new counterfactual setter topics, `WalletUBIDSet` / `WalletUBIDCleared`, and the attestation
   events if they are to be indexed; widen `AgentBound.standard` to 0–7.
4. Before the Ethereum upgrade (#3), rerun the same scan against
   `0xde152AfB7db5373F34876E1499fbD893A82dD336`.
